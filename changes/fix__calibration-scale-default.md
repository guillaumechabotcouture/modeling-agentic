## Changelog

**One calibration scale default, taken from the engine card.** `toolkit/analysis/batch.py` `calibrated_value` read an undeclared `calibration.scale` as `log` while `toolkit/spec/schema.py` documented `linear`, so a spec calibrating `log_rate` on [-8, 2] with no scale gave the engine `exp(z) > 0` as a log rate: an impossible fit that ran into the bound and was refused as a ridge. `schema.calibration_scale` is now the one resolution (the declared scale; else the engine card's valid range for the attribute: a range going below 0 means linear, one from 0 up keeps log; else linear), read through `Spec.calibration_scale()` by the batch, the joint calibration (problem and signature) and the figure-data rebuild check, so an attribute on a range from 0 up (a transmission density, a share, a seed) keeps its log scale and its job hashes; a raw spec mapping resolves the same way (`resolved_scale`, the engine card read), and a failed card read is never cached. Before sign-off, `scale_problems` refuses a declared log scale for an attribute whose card range includes negative values, with the reason (a range from 0 up is accepted: exp(z) reaches as close to 0 as the range asks), and an explicit `scale: null` is refused instead of read as the default. `ridge_refusal` now names the parameters sitting at a bound and, when most do, says to check the attribute's scale or range first; `CalibrationRefused` carries them (`at_bound`) and `analysis/blocked.yaml` records them. Self-tests CR11 (the toy panel with its scale removed now calibrates), CR12 (the refusal names bound parameters; the scale hint only when most are bound) and SP4s-x (the resolver, raw and Spec alike, the pre-sign refusal, a null scale, a log scale on a range from 0 up) failed before the fix.
