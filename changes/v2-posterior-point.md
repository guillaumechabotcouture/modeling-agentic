## Changelog

**A declared net-effect posterior's verified chosen point is the point value of its columns.** Before, each uncertainty draw took whole posterior rows, but the point estimate of a posterior column still came from `fitted.yaml` (fitted kinds) or the card default. The joint calibration held non-shared parameters at that same point, so the headline plan and the calibration could sit at a point the declared fit rejects. Now `uncertainty.net_effect_sample` also reads the fit's verified chosen point (`joint_region.verified.chosen.point`, in the signed bytes that `load_posterior` replays through `finalize()`). That point must equal the fit's recorded `parameters` values. `uncertainty.posterior_point` sets every posterior column to it, in `core.Analysis.theta0` and in `joint_calibration.theta0` alike, as `set_joint` already moves shared parameters to the joint calibration's best point. The same point is used by the pre-run evidence the sign-off checks read (`decision_tests.prerun_evidence`) and by the joint calibration's benchmark settings for a fitted posterior column. Four cases are refused, with no fallback to card or fitted values: (1) a spec `engine_parameters` value for a posterior column more than 1e-6 from the chosen point (the fit file's 6-decimal rounding, whatever the magnitude; an equal value is accepted, so an entry that only makes a column drawn can stay); (2) a posterior file without a chosen point, or with a column missing, non-finite or different from the recorded `parameters`; (3) an empty `uncertainty.net_effect_posterior:` field, which was read as no posterior before; (4) a posterior with `calibration.method` `likelihood` or `posterior`, whose engine parameters are the calibrated ones over engine defaults. An `interaction_rescale` decision test with a posterior reads arm ratios that the harness step (`engine_parameters.py benchmarks`) computed at the chosen point, with fitted columns as fit-mode candidates and the others as base parameters. The record carries `posterior_point`, and `verified_spec_benchmarks` refuses a record whose point is not exactly the chosen point, so the test reports `not_run` with that reason, or when the step was not run. The file's own `posterior_point` is checked too, and a caller's `fitted` entry never overrides a posterior column. A benchmark setting's own observed conditions still win over a posterior column, as they do over spec values, and `superseded` records it (RPP9, θ-ι). The analysis manifest's engine record holds `point_source` (`{column: posterior_chosen_point}`) and `posterior_point`. Specs without the field are unchanged. The self-test fixture `net_effect_fit._fixture_placeholder` now writes a chosen point (default: the first row) and the matching `parameters`. Tests written first and failing before each change: RNP3 and RPP2-RPP6 (RPP4b covers the equal-within-rounding case) in run.py, and PC18 in preconditions (α-β). RPP1 (no posterior: point values unchanged) passed before and after. Codex's read-only review raised six P1s and three P2s. Five P1s were fixed with their cases written first and failing (RPP7-RPP11): the conflict tolerance's scaling, an empty field, the recorded parameters, the likelihood and posterior calibrations, and interaction tests. The sixth P1 was disposed of, not fixed: the joint calibration's benchmark settings hold a shared fitted parameter at its fitted value, which predates this change, and a benchmark setting's own parameters override spec values by design. Two of the P2s were fixed: PC17 and RNP3 now use a chosen point distinct from the fitted value and from the first sample row (γ-δ). Codex round 2 raised two P1s, both fixed with their cases written first and failing. The chosen point must equal the recorded `parameters` exactly, which refuses NaN and values within 1e-6 (RPP10). Its coordinates must be exactly the sample's columns (RPP12). Of the four P2s, two were fixed: the 1e-6 boundary no longer refuses a value exactly 1e-6 away through float subtraction (RPP13), and PC17 now separates the chosen point from the fitted value (the chosen point lies above the hull, the fitted value below). Not changed: an equal spec value for a column of kind `fitted` is still refused at validation, because fitted values are never spec-settable; and the parameter figure shows the card's value, not `posterior_point` (ε-ζ). Codex round 3, the last, raised four P1s and one P2. Two P1s and the P2 were fixed, with their cases written first and failing. A recorded parameter that the sample and the chosen point lack is refused (RPP14). The tolerance allows only the float subtraction's own error, a few ulps at the values' magnitude, so a value 1.0000005e-6 away is refused (RPP15). RPP11 covers the `posterior` method too. Two P1s are narrowed, not fixed. First, the chosen point is checked against the fit's recorded values and against the run's design box (PC17), not against the fit's own search box: a margin that widens the design box can admit a chosen point outside that search box, if the fit file records one. Second, re-running a derived step such as trajectories on a run analysed before this change rebuilds the analysis at the chosen point while reusing that run's plan. Such runs have no `point_source` in their manifest and should be re-analysed, not patched (η).
