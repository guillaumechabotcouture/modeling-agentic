## Changelog

**Launcher handover after a lost connection, and reuse that survives a new commit (F6 S1-8).** Two F5 failures on 2026-11-08. (1) The resume launch submitted the run, the scheduler listed it after 43 s, then the laptop's client lost its connection (`OSError: Timed out trying to connect to tls://...:443 after 30 s`); `launch` raised, a watchdog read that as a failed launch and stopped the keeper cluster, though the run kept going and completed; `clusters.json` had not been written. `cloud/run_cluster.py launch` now prints an invocation token first (or uses the watchdog's `MA_LAUNCH_INVOCATION`), takes a per-config lock, and writes `clusters.json` (run cluster id, launch id, launch time, `status`, invocation) as soon as the run cluster exists, before any submission, through a unique temporary file; later writes refuse a record another invocation owns. Each helper cluster's id is recorded right after its constructor, and every label's assignment is written before the first submission. After each submit it waits, bounded (36 polls, 5 s apart), for the scheduler to accept the run: its held future finished or erred, the scheduler lists it as processing, or holds it queued or waiting (`wait_listed`). Once anything has been submitted the launch never reports a failure: the safe exit code is chosen first, then recording it and printing how to attach later are best effort (interrupts included). It exits 3 (every run listed, then the connection dropped), 4 (acceptance not seen) or 5 (a later step such as the keeper failed). Exit 1 means this invocation submitted nothing, and authorizes stopping clusters only through a `clusters.json` with this invocation's token and status `failed`; a refusal (already running, preflight, lock held) writes no record, so an earlier launch's record is never mistaken for the current one. The codes are in the module doc. `relaunch` has the same boundary (0 or 4 once it has submitted). The new `keeper` command starts the overflow pool and keeper later for the run cluster `clusters.json` records, only while that cluster is the live one. (2) Stored engine rows were recomputed. `scripts/compute.py code_fingerprint` no longer hashes the launch commit stamp (`scripts/lib/code_commit.txt`, filled in by `git archive`), nor, in a v2 run (`decision_spec.yaml` at the run root), the three fixed-name analysis outputs the harness writes under `models/` (`allocation_robustness.yaml`, `claims_spec.yaml`, `claims_ledger.yaml`). Exact paths only: a v1 run hashes everything, and every other file under `models/` or `data/` (decision tests included) is still hashed. It now also hashes the repo's dependency manifests (`requirements*.txt`), and each batch records the orchestrator's runtime versions. The spec is not hashed, as before: what it sets reaches each job through its params, which are the row's key. A batch also records `fn_id`, the function's run-relative or `repo:` identity, because each cloud launch extracts the code to a new temporary directory and an absolute function path never matched twice. `reuse_report` / `compute.py reuse-check <run_dir> [--expect-all]` reports, per stored batch, the rows stored and the rows eligible for reuse (cache eligibility, conditional on identical inputs: it does not generate the next run's inputs) and why not. `run_cluster.py <config> reuse-check <run_dir>` runs the tarball's own `compute.py` on the run dir, locally. Batches stored before this change carry the old fingerprint and are not reused. Self-tests were written first and failed before each change: LR0-LR12 and R1a-R7c, R2a-R2d (`run_cluster.py`: fake scheduler and coiled, the F5 sequence replayed, Codex round 1 on #161) and RU1-RU16 (`compute.py`: temporary trees, a batch reused from a second tree and a moved run dir, a v1 function reading a harness-named file, a dependency-only change, the CLI).
