## Changelog

**Launcher handover after a lost connection, and reuse that survives a new commit (F6 S1-8).** Two F5 failures on 2026-11-08. (1) The resume launch submitted the run, the scheduler listed it after 43 s, then the laptop's client lost its connection (`OSError: Timed out trying to connect to tls://...:443 after 30 s`); `launch` raised, a watchdog read that as a failed launch and stopped the keeper cluster, though the run kept going and completed; `clusters.json` had not been written. `cloud/run_cluster.py launch` now writes `clusters.json` (run cluster id, launch id, launch time, `status`) as soon as the run cluster exists, before any submission, and atomically on every update. After each submit it waits, bounded (36 polls, 5 s apart), for the scheduler to list the run's task key (`wait_listed`). Once anything has been submitted the launch never reports a failure: it records the outcome in `clusters.json`, prints how to attach later (`status`, `health --loop`), and exits 3 (submitted, connection lost: every run listed, then the connection dropped), 4 (submitted, not confirmed: the listing was not seen) or 5 (submitted, launch incomplete: a later step such as the keeper failed with the connection intact). Exit 1 means nothing was submitted, and `clusters.json` names what to stop by id. The codes are in the module doc for an external watchdog. `relaunch` waits for the listing too (exit 4 when it is not seen). The new `keeper` command starts the overflow pool and keeper later for the run cluster that `clusters.json` records, and only while that cluster is the live one. (2) Stored engine rows were recomputed. `scripts/compute.py code_fingerprint` no longer hashes the launch commit stamp (`scripts/lib/code_commit.txt`, filled in by `git archive`) or the analysis outputs the harness writes under `models/` (an explicit list: `allocation_robustness.yaml`, `claims_spec.yaml`, `claims_ledger.yaml`, the v1 script outputs `eligibility_probe.yaml` and `model_comparison_formal.yaml`, and `decision_tests/*.yaml`), nor the input-check records the harness writes under `data/` (`input_checks.json`, `geometry_signoff.json`). Any other file under `models/` or `data/` is still hashed, and so is repo code. The spec (`decision_spec.yaml`, at the run root) is not hashed, as before: what it sets reaches each job through its params, which are the row's key. A batch also records `fn_id`, the function's run-relative or `repo:` identity, because each cloud launch extracts the code to a new temporary directory and an absolute function path never matched twice. `reuse_report` / `compute.py reuse-check <run_dir> [--expect-all]` reports, for every stored batch, the rows stored, the rows that would be reused and why not. `run_cluster.py <config> reuse-check <run_dir>` runs the tarball's own `compute.py` on the run dir, locally, before a launch. Batches stored before this change carry the old fingerprint and are not reused by it. Self-tests were written first and failed before the change: LR0-LR12 (`run_cluster.py`: fake scheduler and coiled, the F5 sequence replayed) and RU1-RU13 (`compute.py`: temporary trees, a batch reused from a second tree and a moved run dir, the CLI, and a check that the harness-output list covers every `models/` path `toolkit/analysis` names).
