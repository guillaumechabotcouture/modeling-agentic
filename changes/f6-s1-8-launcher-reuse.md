## Changelog

**Launcher handover after a lost connection, and reuse that survives a new commit (F6 S1-8).** Two F5 failures on 2026-11-08. (1) The resume launch submitted the run, the scheduler listed it after 43 s, then the laptop's client lost its connection (`OSError: Timed out trying to connect to tls://...:443 after 30 s`); `launch` raised, a watchdog read that as a failed launch and stopped the keeper cluster, though the run kept going and completed; `clusters.json` had not been written. `cloud/run_cluster.py launch` now prints an invocation token first (or uses the watchdog's `MA_LAUNCH_INVOCATION`), takes a per-config lock, and writes `clusters.json` (run cluster id, launch id, launch time, `status`, invocation) as soon as the run cluster exists, before any submission, through a unique temporary file; later writes refuse a record another invocation owns. Each helper cluster's id is recorded right after its constructor, and every label's assignment is written before the first submission. After each submit it waits, bounded (36 polls, 5 s apart), for the scheduler to accept the run: its held future finished or erred, the scheduler lists it as processing, or holds it queued or waiting (`wait_listed`). Once anything has been submitted the launch never reports a failure: the safe exit code is chosen first, then recording it and printing how to attach later are best effort (interrupts included). It exits 3 (every run listed, then the connection dropped), 4 (acceptance not seen) or 5 (a later step such as the keeper failed). Exit 1 means this invocation submitted nothing, and authorizes stopping clusters only through a `clusters.json` with this invocation's token and status `failed`; a refusal (already running, preflight, lock held) writes no record, so an earlier launch's record is never mistaken for the current one. The codes are in the module doc. `relaunch` has the same boundary (0 or 4 once it has submitted). Each assignment records its exact task key before the submission, and `relaunch` refuses while the scheduler still holds that task (queued, waiting or processing, which covers a VM still preparing the run before its `run.log` exists), when its state cannot be read, or when a sent assignment has no key. The new `keeper` command first reconciles the recorded helpers for the run cluster `clusters.json` records (only while that cluster is the live one): a live helper with the recorded id is this launch's and is kept (the keeper only once it is confirmed holding the pool), a live helper with another id is an earlier launch's and is stopped by that id, and only missing helpers are started. `ack-probe` sends a task that returns at once through the acknowledgement and prints what acknowledged it (the smoke's fast-task case). A keeper counts as healthy only with a fresh heartbeat (`keeper_fresh`: a tick with no error or exit after it, a status at most 180 s old by the keeper's own clock, for this run cluster and overflow pool); `keeper` replaces a live keeper whose overflow pool is gone. Cloud-side lifetimes for short jobs: `run_timeout_hours` kills main.py's process group, and `hold_hours` bounds the hold for `collect` (default 24 h, as before). The smoke watch is bounded by the wall clock and bounds every API call. Ownership: a cluster is this invocation's only when it created it. `coiled.Cluster(name=...)` attaches to a live cluster of that name instead of creating one, and coiled 1.135.6 reports which happened only in its log ("Creating Cluster (name: ...)", `coiled/v2/cluster.py:1685`, against "Attaching to existing cluster", `:1688`; it lists no tags). `_construct` therefore requires that no live cluster of the name is listed just before the constructor, that Coiled logged the creation, and that the cluster's `created` time is no earlier than the construction's start less 120 s; otherwise it refuses before the id is recorded anywhere. Each construction's start and outcome go to `<out_dir>/constructions.jsonl`. Clusters still get the tag `ma-invocation=<token>` for people, and the config's `cluster_timeout` (a cloud-side lifetime; empty by default). `smoke-run` runs `launch` as its child, can interrupt it on an output line, and at the limit terminates and reaps it before stopping, by id, every cluster the journal says this invocation created (and any cluster of a name whose construction never finished, created after it began). Two fixes from the real smoke (IDM workspace, 2026-11-09): `ack-probe` connects only to the recorded run cluster id while the listing shows it ready or running, through a plain `distributed.Client`, never the name-based constructor (it had attached by name to a stopping run cluster, and Coiled created an empty one), and exits 6 with "no acknowledgement evidence" when the cluster stops while it connects; `confirm_keeper` ends its wait at once when the run cluster has stopped (about 6 minutes of retries before). The `run_cluster.py` and `vm_job.py` self-test entries run under one shared guard (`cloud/no_cloud.py`) that refuses any use of the real `coiled` module. (2) Stored engine rows were recomputed. `scripts/compute.py code_fingerprint` no longer hashes the launch commit stamp (`scripts/lib/code_commit.txt`, filled in by `git archive`), nor, in a v2 run (`decision_spec.yaml` at the run root), the three fixed-name analysis outputs the harness writes under `models/` (`allocation_robustness.yaml`, `claims_spec.yaml`, `claims_ledger.yaml`). Exact paths only: a v1 run hashes everything, and every other file under `models/` or `data/` (decision tests included) is still hashed. It now also hashes the repo's dependency manifests (`requirements*.txt`), and each batch records the orchestrator's runtime versions. The spec is not hashed, as before: what it sets reaches each job through its params, which are the row's key. A batch also records `fn_id`, the function's run-relative or `repo:` identity, because each cloud launch extracts the code to a new temporary directory and an absolute function path never matched twice. `reuse_report` / `compute.py reuse-check <run_dir> [--expect-all]` reports, per stored batch, the rows stored and the rows eligible for reuse (cache eligibility, conditional on identical inputs: it does not generate the next run's inputs) and why not. `run_cluster.py <config> reuse-check <run_dir>` runs the tarball's own `compute.py` on the run dir, locally. Batches stored before this change carry the old fingerprint and are not reused. Self-tests were written first and failed before each change: LR0-LR12 and R1a-R7d, R2a-R2d, R8-R8e, R9-R9f, K1-K2, G1-G2, W1-W6, T1-T3, O1-O5 (`run_cluster.py`, `vm_job.py`: fake scheduler and coiled, the F5 sequence replayed, Codex rounds 1 to 4 on #161) and RU1-RU16 (`compute.py`: temporary trees, a batch reused from a second tree and a moved run dir, a v1 function reading a harness-named file, a dependency-only change, the CLI).
