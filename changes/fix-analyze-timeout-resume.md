## Changelog

**v2: the analyze step's time limit follows the run's compute cap, and a run stopped by that limit can be resumed.** The Nigeria v2 full run (2026-11-02) went from ANALYZE to FINAL with `run_failed`: `scripts/pipeline.py` killed the analyze step at its fixed 1-h default (`DEFAULT_TIMEOUT_S`) with 184 of 256 design points done, because `toolkit/analysis/api.py` gave the step no `timeout_s`. Three changes. (1) `scripts/compute.py` `step_wall_s()` derives the limit from the existing compute settings: the run cap (`MA_COMPUTE_MAX_CORE_HOURS`, default 200 core-hours, now the shared constant `RUN_CAP_CORE_HOURS`) spread over the target pool (`MA_COMPUTE_TARGET_WORKERS` × `MA_COMPUTE_PROCS_PER_WORKER` or `MA_COMPUTE_CORES_PER_WORKER`, default 8), doubled, plus one hour for the step's own work, at most 24 h. With no cluster settings it returns None and the runner's 1-h default still applies (local and toy runs). A value that does not parse is a ValueError, so the run fails at CONFIGURE before any compute. `api.pipeline_steps` sets this limit as the analyze step's `timeout_s`. (2) `agents/stage_machine.py`: when the analysis step times out, or is killed by SIGKILL, SIGTERM, SIGINT or SIGHUP, the ANALYZE → FINAL entry in the history records `resumable: timeout|killed`. `main.py --v2 --resume <run>` (`run_v2` → `Machine.reopen_interrupted_analysis`) then puts the run back at ANALYZE, recorded as FINAL → ANALYZE with `resumed_from`. It rewrites `models/pipeline.yaml` so the limit follows the current budget, and the engine batch reuses the rows it had already finished. The classification is read from the harness's `models/pipeline_report.json` (`resumable_failure`), so runs that failed before this change are classified the same way. Every other `run_failed` cause (an error exit, a crash, a configure or spec failure) stays terminal. (3) `scripts/compute.py` `code_fingerprint` no longer hashes the pipeline runner's own files in `models/` (`pipeline.yaml`, `pipeline_state.json`, `pipeline_report.json`). The runner writes them when a step fails, so before this change a rerun after a timeout discarded every partial row. (4) `scripts/pipeline.py` `_run_cmd`: after a timeout kill, the runner waits at most `KILL_GRACE_S` (10 s) for the step's pipes to close. A process that had left the step's process group still held them open; compute.py's local pool processes make their own group, so one orphaned at spawn did this. Before the change the runner waited until that process exited, which took 10 minutes in testing. Tests, written first: AP8 (`toolkit/analysis/api.py`), SW1-SW5 (`scripts/compute.py`), PL15b (`scripts/pipeline.py`), T58-T60 (`agents/stage_machine.py`: a toy compute batch timed out at 3 of 6 rows, resumed, and only the 3 missing rows computed). Retro on the collected run directory: the run's settings (8 target workers, 150 core-hours) give `timeout_s` 20475 (5.69 h), and the run is classified `resumable: timeout`.
