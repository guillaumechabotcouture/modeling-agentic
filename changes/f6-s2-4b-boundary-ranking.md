## Changelog

**Emulator ranking near package switches, against engine runs at the calibrated values (F6 S2-4 part 2).** The third gap of critique finding C5: nothing checked whether the emulator orders packages correctly where the plan is closest to switching. On the emulator path the analysis now picks the units whose point-plan package is closest to switching. Closeness is the relative gap in benefit per cost between the plan package and the runner-up, which is the feasible, non-comparator package with the best benefit per cost among the others. Units whose plan package is the comparator are not candidates. The number of units is `boundary_units` in `toolkit/analysis/thresholds.yaml` `emulator`, proposed at 20. Each picked unit is run on the engine at its calibrated value and the point parameters, for the comparator, the plan package and the runner-up. The design's held-out points cannot serve as the held-out set: they sit at Sobol values of the calibrated attribute and of the parameters, not at the units' calibrated values where the plan is defined, and few of them are boundary units. So the check makes its own engine runs, in one shared-state task per unit: the comparator, the plan package, the runner-up, and each of the two without one of its components, because an incremental per-outcome cost item reads that package. That is 3 runs per unit when both packages have one component, and up to 3 + the two packages' component counts otherwise. The engine-side benefit and cost are evaluated twice, with the packages not run filled by two different values; if the compared packages move, the check fails closed, so no emulated value reaches the engine side. They go through the design batch's compute path, provenance check and stored-row reuse (`analysis/boundary/results.jsonl`). The engine's benefit and cost are computed by the analysis's own evaluation (`toolkit/analysis/core.py`), and the order of the two packages is compared with the emulator's. A unit whose two engine ratios are within `boundary_tie_rel_gap` of each other (proposed at 1%) is an engine tie: either order loses at most that share, so it counts as matched, and the artifact counts the ties. `analysis/emulator_boundary.yaml` records the units, the matched share, the ties, each unit's ratios in both models, the held-out source and the number of engine runs, and `results.md` gives the share. The artifact also records the ratio table (every unit whose plan package is not the comparator, with the benefit per cost of each feasible package). The gate (`toolkit/analysis/contract.py`) rebuilds the candidates from that table and checks it against its own expectation: the table must cover exactly the units the point plan (`analysis/point.yaml`) funds with a non-comparator package, each with its plan package and every package feasible for it under the signed spec. The rows must be exactly those candidates, with the table's emulator ratios. It then re-judges the share from the rows, never from the stored verdict; a missing or non-finite ratio never counts as a match. Whether the artifact is required comes from the signed spec's `analysis.evaluation`, not from the manifest, so an emulator-path run without it is a finding, older completed emulator runs included. A share below `boundary_rank_agreement_min` (proposed at 0.8) is a finding, `emulator_boundary_ranking`, that the owner can declare. Counts that disagree with the rows, and an unreadable artifact, are findings the owner cannot declare. A run in which no unit has a runner-up is not judged, which is different from a pass. The new thresholds sit outside the `calibration` and `estimates` sections that the evidence digests bind (#168), so changing them restamps no engine evidence. The direct path is unchanged. Self-tests: `boundary.py` BD1–BD6, `run.py` BD-R1–BD-R3 (the engine side equals the engine evaluated directly at the calibrated values; the artifact is required by the evaluation mode).
