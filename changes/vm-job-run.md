## Changelog

**One command launches a VM job, waits for it and stops the cluster.** On 2026-11-03 an agent ran `cloud/vm_job.py up`, ended its turn to wait for the cluster, and never sent `start`; the VM idled out after 20 minutes with no job submitted, and about two hours were lost. `vm_job.py run <name> <job_id> --store <prefix>` takes every `up` and `start` option. The job id, the command and the shipped tree are checked before anything is created. It creates the cluster, submits the job as soon as the first worker is up, prints a status line every `--every` seconds (default 60; outputs saved locally on each poll), then stops the cluster. `--store` is required: success means the job is done and every output is verified in storage. Anything else exits non-zero with the reason after the last poll: a failed, timed-out or lost job, an unverified copy, or a cluster that stopped before the final state was read. The cluster is stopped whatever ends the command (success, failure, an error, Ctrl-C), unless `--keep-on-failure` and the job did not succeed. `run` names its cluster `<name>-<job_id>-<6 hex>` (lowercase, at most 63 characters) and records the name and id in `job.json`, so ownership is the unique name: no same-name launcher can race it. A constructor that allocated a cluster and then raised or was interrupted before returning an id is stopped by that exact name. A refusal, or a failure before the constructor call, stops nothing. `status`, `wait` and `down <name> <job_id>` find the cluster through `job.json`, so nobody types the suffix; `up` and `start` are unchanged. A live cluster named `<name>`, or one already running for the same job (the name prefix is truncated as real names are), is refused. A second `run` of the same job with the same `--out` is refused by a lock on the job's local directory, held for the whole run, before anything is listed or created. Open limit: the lock is local to one `--out` directory, so the same job launched twice at once from two machines, or from one machine with two different `--out` directories, is not detected. Each launch then owns its own uniquely named cluster and stops only that one, so the cost is duplicate work; it never touches a foreign cluster. `run` keeps the cluster object it created for its client and stops the cluster by id (`coiled.delete_cluster(cluster_id=...)`), so it never attaches by name. Polling errors, a failing cluster listing included, are retried. Every poll (`run`, `wait`, `status`) goes to the job's own worker, recorded in `job.json` at submission: with several workers, another worker's disk reads `missing`. The job's worker missing from the table on three polls in a row (an empty table included) reads as `lost`. While the job uploads and reads back its outputs, a heartbeat thread keeps its state fresh, so a long upload never reads as `lost` (which would stop the cluster before verification). Laptop-independent cleanup: under `run` the job stops its own cluster at the end, whatever the outcome (only on success under `--keep-on-failure`; `worker_side.job_task(shutdown_always=)`), after two poll intervals plus a minute (`shutdown_grace_s=`), so `run` normally reads the final state and stops it first. A state write that fails (disk full), the first one after the job claims its id included, does not skip that stop. Either stop request is harmless when the other came first (`_shutdown_cluster` drops the request on a stopping cluster; `run` skips a cluster already stopping). Coiled 1.135.6 counts `idle_timeout` from cluster start and has no "after the first task" setting, so `up` now warns that the cluster stops after its idle timeout unless `start` follows. The `cloud-compute` skill, README and `vm_job.py` docstring make `run` the default. Self-tests RN1-RN19 and RN21-RN24 (`vm_job.py`) were written first and failed before the change: α for the command, γ, ε and η for three Codex review rounds, ι for unique names, λ for Codex round 4, ν for its verification (a fake coiled with `list_clusters` and `delete_cluster`, vm_job's own guard, client and stop code unmocked). RN20, added for coverage, runs the job in its own thread, concurrently with `run`'s polls; it passed before the ζ fix. No cloud run.
