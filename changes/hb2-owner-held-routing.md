## Changelog

**Owner decisions are asked once, at the first gate, and an accepted plan-changing decision test lets the run accept (hb2 fixes 1, 3 and 4; owner decision (b)).** Harness baseline hb2 (triage §4.2, §4.3): in 6 of 8 runs the only open HIGHs were `decision_test_changes_plan` findings, which rule 2 sent to a fix loop that could plan no task for them, twice, before rule 3o asked the owner at the round cap (two wasted critique rounds per run, US$11.89 over the six runs); in malaria R2 the critics re-raised two answered findings, reworded, in every round, and each rewording was asked again (23 OWNER_DECISION visits over the baseline); and in dengue R2 a blocking harness gap was sent to the fix loop twice by rule 4m. **Owner decision (b), 2026-11-23:** an owner-accepted (or, under `--signoff lead`, lead-provisionally accepted) `decision_test_changes_plan` finding may lead to ACCEPT, not DECLARE_SCOPE; the report states the dependence prominently (which input, which units change, that the owner accepted it), and under lead sign-off marks it provisional. This replaces #327's contract (rule 3o then 3, DECLARE_SCOPE). A declined or unanswered plan-changing test still cannot ACCEPT. Changes. (1) `agents/stage_machine.py apply_owner_rule` marks a decision-bearing finding of kind `decision_test_changes_plan` `owner_resolution` (both backends emit it; `departure_test_ineffective`, the other `decision_bearing` kind, is non-declarable and unchanged, and the policy-mapped owner kinds of `scripts/scope_signoff.py`, such as `allocation_unstable`, keep rule 3o and DECLARE_SCOPE once accepted). `scripts/validate_critique_yaml.py _recompute_action`: with rounds left, an unanswered owner-resolution HIGH is put to the owner at once (new rule 2o, AWAIT_OWNER), beside any other finding; once accepted it moves from `unresolved_high` to `owner_accepted_high` and no longer blocks ACCEPT (`_incorporate_rigor_violations` carries `owner_resolution`, `owner_signed`, `owner_declined`; `_append_synthetic_blockers` counts the moved entries, so the fold stays idempotent). The ledger records the accept on the gate row (`owner_accepted`, by owner or lead, provisional; reopened when the gate reads the test as asked again, fixed when it is gone), `open_findings` leaves it out, and `render_report` heads the report, after the status and provisional lines, with "The plan depends on inputs the owner accepted": per test, the input it varies, at each plan-changing value the number of units that change package and their ids, the re-solved plan and whether the delivered plan is feasible there, and who accepted it (`dependence_lines`). `toolkit/analysis/moves.py compare` now records `units_changed_ids`, the units whose package changes (MV2b). A rule-2 gate whose HIGHs are all critic findings the owner holds or declared harness gaps declares them now (new rule 3h, `apply_held_rule`). `_shortcut_held` no longer needs rule 4m: a rule-2 gate whose HIGHs are each a critic finding that is the write-up's, the owner's or a harness gap also goes to WRITE in that round; `_fixable_open` leaves out harness gaps. (3) `agents/findings_ledger.py answer_fingerprint` binds a critic finding's answer to its id, kind and remedy class (`remedy_class`: an "Owner amendment:" remedy or a fix), not the critic's text, so a reworded re-raise keeps its answer and is not flipped open and accepted again at each sync; a materially different finding (another kind or remedy class) is asked again, the #258 rule. A harness finding's claim (measured evidence the harness writes, e.g. a conflict's verdict) stays bound (R3-8). `scripts/scope_signoff.py`'s item fingerprint is unchanged: it covers gate findings only (critic-derived ones are skipped) and binds their evidence. The critics are told which of their findings the owner answered, to carry them forward under the same id with the same remedy class (`agents/v2_sdk_tasks.py owner_held_note`). (4) A harness gap's ledger event carries the finding's fingerprint (`FL.harness_gaps`); `apply_medium_rule` leaves such a finding out of rule 4m's tested ones (it is declared, rule 3m, with the reason) and the fix loop's write-up route no longer stops on a blocking harness gap. Codex round 1: an answer recorded under the fingerprint used before (claim and remedy) still binds the finding as asked, so a resumed run keeps a recorded decline (`FL.legacy_fingerprint`, `answer_for`; L22); a harness gap binds the remedy's text too, so a remedy revised within its class is planned again (`harness_gap_key`), and the harness's default plan plans no task for a declared gap; rule 3h never declares while a finding with a test (a MEDIUM too) is neither the owner's nor a gap; rule 2o's request holds only the owner-resolution findings (`scope_request_view`), a policy-mapped item waits for the round cap; the accept records which backend's record it bound and that record's result hash, and the report reads that record, says a result changed since the accept is asked again (no values repeated), counts units against the reference plan the tests use (the point-value plan under `deliverable.plan: expected_value`), names a price case's cost items and multipliers, lists every unit, flags a change not settled within the solver's gap, and gives a spike record's measured effects. Left as designed (lead's brief): two "Owner amendment:" remedies of the same finding share an answer, even when the requested amendment differs; the critics are told to raise a new finding for what the answer did not cover. Codex round 2: when answers under both fingerprints bind a finding, the owner's comes before the lead's and a decline before an accept, and a row whose binding answer is a decline is not kept accepted (L23); an accepted test stays non-blocking over repeated syncs, and one a gate (post-write too) no longer reports is closed and leaves the report (L24); the report recomputes the item's fingerprint from the record there now and hashes a toolkit result on the bytes it reads, so a record changed since the accept is said to be asked again, never shown as accepted; it reads the spike producer's per-value results; under `reference_plan: point_plan` it says the tests measured the point-value plan's dependence, not the delivered plan's (HB2-6); the sign-off page says that accepting a plan-changing test lets the run finish accepted with the dependence at the top of the report, not that it is an untested declaration (SO43); the rule-2 shortcut keeps the round for a non-blocking MEDIUM a task can work to (HB2-4); the fix planner may not plan a task for a declared harness gap, and the default plan's gap entries pass the plan check (F20c).
