## Changelog

**The toolkit path reads its own allocation-stability record (check-value item 5; owner decisions of 2026-11-23).** `toolkit/analysis/run.py` writes the leave-one-group-out allocation stability (`analysis/stability.yaml`), but no harness finding read it. `allocation_unstable` existed only in the spike backend, which no v2 run uses. New `toolkit/analysis/contract.py stability_findings(run_dir)`, added by `toolkit/analysis/api.py gate_findings` beside the decision-test findings (not a contract finding: `gate_findings` is unchanged). It finds the manifest's artifact of kind `stability` under any name, reads it once with no link followed, and hashes the bytes it parses. (1) An UNSTABLE package-identity or value verdict is a HIGH `allocation_unstable` (key `stability`), scope-declarable and decision-bearing. Its claim names the groups whose exclusion changes the plan, the worst fold's units and share, and the share of units that change package in at least one fold. It says when the folds are counted against the point-value plan (`deliverable.plan: expected_value`). It carries the record it was read from (`stability_record`). (2) A record that cannot be verified or read, an unknown verdict, malformed folds (no group or unit count, a share outside 0 to 1, totals that disagree), or a spec without a completed manifest is a non-declarable HIGH `analysis_contract_stability` (fail closed). The no-manifest one is dropped when the contract checks already report the analysis as missing. (3) NOT_RUN on an allocation run is no gate finding: `contract.stability_note` gives an advisory note (`stability_not_run`, with the reason and what would run it). `render_report` lists it under "Advisory notes (no effect on the outcome)". It is never declared, never planned as a fix task and never changes the outcome. Routing, owner decision 1: `agents/stage_machine.py OWNER_STABILITY_KINDS` applies to the toolkit's decision-bearing `allocation_unstable` only; the spike's keeps the policy map. `apply_owner_rule` marks it `owner_resolution`, so rule 2o asks the owner at the first gate, as #357 does for `decision_test_changes_plan`. The item binds the finding's own record and the disposition `accept_with_dependence_stated` (`DT_DISPOSITION`). It is kept out of `scripts/scope_signoff.py`'s policy map, which would ask it again under another fingerprint. An accept by the owner, or the lead's provisional one under `--signoff lead`, lets the run ACCEPT, like decision (b): the item moves to `owner_accepted_high`. A decline is `scope_declaration_declined` and the run cannot accept. `stability_dependence_lines` heads the report with each accepted item: its claim (the groups, the share of units) and who accepted it. It is shown only while the record there now has the accepted fingerprint; otherwise it is stale and an accepted report is withheld (`_render_stale`). The sign-off page describes the item as a measured change whose accept lets the run accept (`_accepts`), and the provisional list counts it as plan-changing. `agents/findings_ledger.py owner_resolved` closes the ledger row when a gate no longer reports it and reopens it when a gate asks again. Retro (read-only, the 31 v2 runs of the check-value analysis: hb0 to hb2, the earlier evals, Nigeria F2 to F6 run 4). 8 runs raise `allocation_unstable`, an owner item at the first gate (7 Nigeria, 1 hb). 14 runs get the advisory note (8 hb, 6 earlier). The reasons are no `analysis.stability.holdout_group` in the spec (13) and `calibration.method: none` (1). 9 runs get neither: 7 estimates runs, 1 ROBUST run, and 1 Nigeria run whose UNSTABLE record sits under a manifest with no completion status. That run's no-manifest finding is dropped beside the contract's own. Codex round 1 (8 P1s, at the earlier declare disposition) is fixed: plan wording; the measured item is shown as plan-changing, not untested; one read binds claim and hash; the report checks the accept against the current record; the no-manifest race; artifact by kind; fold validation. The P2 on the NOT_RUN remedy is fixed. The P2 on planning a `fix_task: False` finding is closed by the advisory note. Self-tests K-ST1 to K-ST11 (`toolkit/analysis/contract.py`), AP11 (`toolkit/analysis/api.py`), OR-V8 (`scripts/validate_critique_yaml.py`), SO-ST1 to SO-ST6 (`agents/stage_machine.py`).
