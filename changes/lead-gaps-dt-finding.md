## Changelog

**The default toolkit backend emits `decision_test_changes_plan` (closes the first known limit of 1F, #316).** The toolkit backend recorded each decision test's verdict in `analysis/decision_tests.yaml` but emitted no finding, so the 1F owner lifecycle (owner request at OWNER_DECISION; under `--signoff lead` a provisional answer flagged above the draft) fired only on the spike backend. `toolkit/analysis/api.py gate_findings` now returns, after the contract checks, one finding per test whose verdict is `CHANGES_PLAN` (`contract.decision_test_findings`): kind `decision_test_changes_plan`, HIGH, stage ANALYZE, keyed by the test id, `decision_bearing: true`, scope-declarable only through the owner rule, the same shape the spike backend emits and `apply_owner_rule` consumes. A test settled only within the solver's gap still carries the verdict, so it is included. The rows are read only from the artifact a completed manifest lists with a matching hash; a missing, changed or unreadable artifact gives nothing here because `contract.gate_findings` already reports it as a non-declarable HIGH. `contract.gate_findings` itself is unchanged: a plan-changing test is not a contract failure, and every existing "the contract checks pass" assertion stands. The owner item's fingerprint (`stage_machine._bearing_item`) now binds the verified toolkit row (`contract.decision_test_record`) when the spike's `analysis.json` has none, so a changed result is asked again. The claim names the test's statement and, when recorded, the share of units changed, the regret and the dollars moved, with what triggered the verdict. Behaviour change, visible in T36: the toy spec's automatic `fitted_range_*` tests change the plan, so the default-backend end-to-end run under `--signoff lead` now answers them provisionally (it never pauses), flags them above the draft and ends `completed_scope_declared` instead of `completed`. T36 keeps every earlier check (manifest, fix row, D-001 fixed) and now also asserts that the provisional plan-changing answers are exactly the run's CHANGES_PLAN tests, that each is named above the draft, and that the run never paused. Codex round 1: the artifact is read once with no link followed and hashed on the bytes parsed; a completed manifest (`status: complete` and `complete: true`) whose artifact cannot be read and verified gives one non-declarable HIGH (`analysis_contract_decision_test`) instead of an empty list, so a plan-changing test is never dropped silently; the owner item binds its producer's record only (a toolkit finding the verified row plus its result file's hash, which holds the per-value plan hashes; a spike finding `analysis.json`), so a stale file of the other backend or a different plan with the same summary is asked again; the claim shows the test-level share of units changed against its threshold and names what triggered the verdict (regret and dollars are per tested value, so they are named, not quoted); T36 reads the expected tests from the artifact itself and requires at least one. Codex round 2: the owner item also binds the headline plan's hash (`analysis/point.yaml`), so the same test result over a different headline allocation is asked again; a spec without a completed manifest (a rerun may withdraw it between the contract checks and this read) gives a non-declarable HIGH, which `api.gate_findings` drops only when the contract checks already report the analysis missing, incomplete or blocked. A decision-bearing finding before the last round still goes to the fix loop first (1F's known limit, unchanged). Self-tests K-DTP1-K-DTP7 (`toolkit/analysis/contract.py`), AP9-AP10 (`toolkit/analysis/api.py`), T_DT_TOOLKIT_FP, T36 (`agents/stage_machine.py`).
