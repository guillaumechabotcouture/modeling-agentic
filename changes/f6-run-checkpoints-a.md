## Changelog

**Run checkpoints on the agent VM, fetch and resume from them, and a final checkpoint before the watch stops a launch (F6).** On 2026-11-11 the F6 preview ran 3 h and was stopped at its spend cap by `cloud/launch_watch.py`. A v2 run stores its run directory only when `main.py` ends, so nothing was stored and 3 h of engine batches were lost. (1) While `main.py` runs, `cloud/worker_side.py` `Checkpointer` uploads a tarball of the run dir every `checkpoint_minutes` (new `RunConfig` field, default 15, 0 off) to `outputs/<storage_prefix>/launch_<id>/checkpoint_<label>.tar.gz`, then its record `checkpoint_<label>.json` (time, size, sha256, run state and round, cached engine batches and rows). The tarball (`runs/<RUN>/...` and `run.log`) is built by the new `scripts/results_store.py` `write_archive` with the final store's exclusions (no `_truth/`, no credential files, API keys redacted); `upload_file` streams it and verifies the read-back. One upload runs at a time, a checkpoint due while one uploads is skipped, and a failure is logged and never stops the run. (2) `run_cluster.py <cfg> checkpoint [--label L]` downloads the latest checkpoint and refuses on a sha256 mismatch; `collect` says when a label has only a checkpoint; `checkpoint-now` asks the running thread for one checkpoint, bounded. (3) Resume steps are in the `run_cluster.py` module doc ("Checkpoints"); a run dir restored from a checkpoint reuses its finished engine batches and its interrupted batch's journal (`scripts/compute.py` reuse path). Known limit: a file over 64 MB under `models/` or `data/` is fingerprinted by size and mtime, which tar does not keep, so it makes every batch recompute (`reuse-check` shows it). (4) `launch_watch.py` runs `checkpoint-now` once, bounded, before the stops at its spend cap and at `--max-hours`; a failure never delays the stop, and the exit message names the checkpoint. Self-tests written first: CK1-CK12b (`run_cluster.py`), LW19a-LW19d (`launch_watch.py`), CP0-CP3 (`compute.py`), S8-S9 (`results_store.py`). Codex round 1 (each fix test-first): (P1-1) `scripts/compute.py` run_map's summary records `out_sha256`, the sha256 of the results file it describes, and `_reusable` reuses a finished batch's rows only when the results file matches it (a summary from before this field must at least count its rows), so a snapshot taken between the two writes recomputes that batch, logged; the checkpoint record's state and counts are read from the archive, not the live run dir. (P1-2) `results_store.write_archive` opens each file once, following no link at any component, regular files only, copies it to a temporary file and scans and archives that copy, so a rewrite or a swap for a link to `_truth/` after the listing can neither leak a secret nor reach the answer keys. (P1-3) `checkpoint_now_side` only files a request and returns its token at once (nothing waits on the worker's event loop); `checkpoint-now` then polls storage for a generation carrying the token or started after it. (P2-4) Each checkpoint is an immutable generation `checkpoint_<label>_g<N>.tar.gz` with its record `_g<N>.json`, then the pointer `checkpoint_<label>.json` names it; the last two complete generations are kept, and `checkpoint` falls back to the previous one when the latest does not verify. (P2-5) A checkpoint needs free space of 1.5 × the run dir + 2 GB, else it is skipped (logged); partial and local archives are removed on failure and after upload. (P2-6) `checkpoint-now` connects to the run cluster id `clusters.json` records (never by name) and refuses a record of another invocation or launch, or assignments of another launch; `launch_watch.py` passes its own invocation and launch id. (P2-7) A request made while an upload is busy stays pending and is met only by a checkpoint that started after it. (P2-8) Every label is requested first, then all are awaited under one deadline. Tests: CK13-CK20 (`run_cluster.py`), S10-S13 (`results_store.py`), CP4-CP6 (`compute.py`; CP4 is the hop through the launch tree: committed with `add -f`, archived, extracted, rows reused), LW24 (`launch_watch.py`). Codex round 2 (test-first): (P1-1) a name is split on "/" only and never translated, a component that is empty, "." or ".." is refused, and the run dir itself must not be a link, so a file named `..\..\x` is that file and a run dir linked into `_truth/` is refused (S14-S15). (P1-2) Generations are numbered after every one already stored for the launch and label (listing and pointer read from storage; unreadable: no checkpoint), the pointer names the new one and its `previous`, and only generations older than both are deleted, after the pointer is published: a checkpointer recreated on a lost work dir whose record uploads fail leaves g1, g2 and the pointer intact (CK21-CK21b). (P2-3) A checkpoint needs free space of 2.2 × (largest file + run dir) + run.log + 2 GB: the archive being written beside the temporary copy of the file being added (CK22, a sparse 10 GiB fake). (P2-4) A request whose checkpoint is skipped (no run dir, disk) or fails is requeued and retried after 30 s, at most 10 times (CK23). (P2-5) `checkpoint-now` asks every worker at once, one thread each, and every blocking call (connect, worker request, storage read) takes the time left under the one deadline; an unresponsive worker is reported as unavailable (CK24). Codex round 3 (test-first): (P1-1) the run dir is reached from the job's work dir one component at a time with no link followed, and files are listed and opened through that directory fd, so a parent link such as `work/runs` into `_truth/` is refused (S16, CK29). (P1-2) once the pointer upload has been attempted, that generation is never deleted, even when its read-back fails; retention deletes only generations older than both the new pointer's generation and its `previous` (CK25-CK25b). (P2-3) generations with no pointer (a VM lost before its first) are not a dead end: the newest complete generation (tarball matching its record's sha256) is adopted as the base; only a pointer that is listed but cannot be read refuses (CK26-CK26b). (P2-4) run.log counts as one of the archived files in the disk check (CK22b). (P2-5) each request counts its own tries; exhausting one drops only that one (CK27). The `checkpoint-now` deadline is checked before every blocking call, with no grace after it (CK28: 30 hanging storage reads end at a 0.3 s deadline). Codex round 4 (test-first): (P1) a capture is kept only when `run_state.json` read before the listing, read again after the archive is written, and as archived are the same bytes; otherwise (a report copied, then quarantined while `FINAL` / `completed_no_report` was written) the archive is discarded, never uploaded, and retried once on the next tick, then at the next interval (CK30). (P2) `checkpoint` without a pointer adopts the newest complete generation, as the uploader does (`worker_side.newest_complete`, CK31). (P2) a candidate generation's sha256 is hashed as its blob streams (`results_store.sha256_blob`: chunks, never read whole or written to disk; CK32, S17 with a 200 MiB stream). The large-file limit above stands. The dollar cap measured from Coiled's bill, the checkpoint requirement and the signed-budget check follow in a separate PR.
