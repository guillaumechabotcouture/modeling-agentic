## Changelog

**Paid launches are refused unless the owner-signed budget covers them (F6 S2-BG2).** This builds on S2-BG1 (`cloud/budget.py`). `cloud/vm_job.py run`, `up` and `start` require `--cap-usd`. `--budget-scope` defaults to the scope whose prefix the name has. They refuse unless `budget.launch_budget_ok` holds, before any job is submitted, and for `run` before any cluster is listed. `run` reserves the cap under the unique cluster name it will create (`<name>-<job_id>-<6 hex>`), so two jobs never share a reservation. `up` reserves only once it will construct a cluster, so an `up` that finds the cluster already up reserves nothing. Interactive `start` keeps a paid cluster busy, so it checks again without reserving; `start` inside `run` is not checked twice. Each `run` poll saves the outputs, then reads the job cluster's USD (`budget.job_meter`, by that cluster's id) before it returns any state, the job's loss after three missing-worker polls included. The cluster is stopped by id, even under `--keep-on-failure`, in three cases: at the cap (after one last copy of the outputs), after three failed readings in a row, or after a failed reading at a terminal state or at the polling deadline. `RunConfig` gains `cap_usd` (required to launch, validated at load) and `budget_scope` (default resolved from `cloud/budget_scopes.yaml` by the name's prefix). `run_cluster.py` calls `budget_guard` on every path that creates or keeps paid work. `launch` reserves, before any key is read or cluster created. `keeper` reserves only when it must start an overflow pool or keeper, after reconciling the healthy ones. `relaunch` does not reserve, and checks before it submits. `scripts/replay_coiled.py launch` (`replay.py run --backend coiled`, new `--cloud-cap-usd`) checks and reserves before it creates, attaches to or grows a cluster. The archived launchers in `docs/experiments/launchers/` refuse at import unless `MA_ALLOW_EXPERIMENT_LAUNCHERS=1` is set, as their README now says. `scripts/cloud_batch.py` (Azure Batch, billed outside Coiled, so the ledger cannot see it) refuses pool creation and task submission unless `MA_ALLOW_AZURE_BATCH=1`. The README and the `cloud-compute` skill name `--cap-usd`. Self-tests were written first and failed before each change: RN28-RN31 (`vm_job.py`; RN29 checks that only the job's own cluster is read and that the output written just before the cap is saved, RN29d-RN29f the terminal branches and the deadline, RN30b/RN30d the `up` reservation), BU1-BU6 (`run_cluster.py`; BU5b a healthy keeper reserves nothing, BU6 the archived launchers' guard), C7 (`scripts/replay.py`) and AB1 (`scripts/cloud_batch.py`). The earlier cases pass `--cap-usd` and a stand-in gate.

## Status
