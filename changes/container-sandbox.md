## Changelog

**A derivation sandbox for unprivileged containers (`audit-hook`).** Inside an unprivileged Docker container, the outside benchmark's setup, bubblewrap cannot create namespaces. Every derivation failed closed, and with the development flag the run ended at SPEC on the HIGH, non-declarable `derivation_unsandboxed`. On Linux, when neither `bwrap` nor `bwrap-sudo` passes its probe (or bubblewrap is not installed), `scripts/pipeline.py sandbox_kind()` now probes a third kind, `audit-hook`. The derivation runs in a child Python (`-I`, the same scrubbed environment, cwd its private work directory, the same caps set strictly). Inputs and the script are copied in read-only and their hashes checked after the run. A PEP 578 audit hook, installed after numpy, pandas and pyyaml load, refuses socket calls, process creation and signals, ctypes, links, writes, renames and removals outside the work directory or onto an input, reads and listings of the run directory, and the introspection that could reach the hook. The script's imports of network, process and foreign-code modules are refused even when a library has already loaded them. A probe script must meet every refusal before the kind is used. If no kind passes, derivations fail closed as before, and macOS is unchanged. The record holds the kind, why bubblewrap was not used and the container's own network (`/sys/class/net`). The report renders a "Derivation sandbox" block with what the kind guarantees, including that the fallback is not a kernel boundary against a script written to escape it. An `audit-hook` record raises no `derivation_unsandboxed`. Guarantees table: `docs/design/v2-derived-inputs.md` §7. Self-tests DI-A0 to DI-A8 (scripts/pipeline.py; DI2 accepts the fallback's refusal) and T13s (agents/stage_machine.py).
