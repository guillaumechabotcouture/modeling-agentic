## Changelog

**A decision spec names only a registered engine.** Found reviewing the agent-built-engines design (#363, open question 15): a spec could name an engine reference the import policy allows but the engine registry does not hold (for example `toolkit.engines.hooks:ToyScheduleEngine`), and it resolved and ran, outside the card, eligibility and benchmark checks the registry carries. `toolkit/spec/schema.py` `check_engine_ref`, which every spec engine path goes through (`Spec.engine`, `load_engine`, `engine_class`, engine: auto candidates and `engine_choice.json` in `_resolve_engine_choice`, `agents/analysis_backend.py` `_card`, `toolkit/engines/benchmark.py` `load_engine`, the spike loader and the batch workers), now refuses a reference outside `REGISTERED_ENGINES` and names the registered ones. `validate` reports it first, so it is a pre-sign problem (`pre_sign_problems`, `signoff.sign`), and the analysis refuses it again when it validates and builds the engine (fail closed). The list lives in `toolkit/` because engine workers receive `toolkit/` and `scripts/` only; `analysis_backend` self-test B_REGISTRY holds it equal to `ENGINES`. Self-tests extend the registry in their own process only (`import_guard.register_test_engine`, carried to their workers by the existing pool initializer); no spec field, file or environment variable is read. The self-test toy engines that `allow_test_refs` enables count as registered. Fixtures that used an unregistered toy (`ToyConditionalEngine`, `ToyScheduleEngine`, `SharedStateToy`, `ToyPriorEngine`) register it. G24 now expects the malaria engine's alias import to be refused as unregistered. Self-tests ER1-ER6, B_REGISTRY, ER-SIGN1-2, ER-ANALYZE1-2 (failing before the change).
