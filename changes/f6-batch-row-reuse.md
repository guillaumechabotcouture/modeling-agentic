## Changelog

**The outcome and boundary batches reuse stored rows by job_sha, engine identity and adapter digest.** F6 run 2 (2026-11-17) stopped in its fix loop with its outcome batch (8,192 jobs) and boundary batch computed. A resume, or any re-analysis in a fix round, would have recomputed both. `compute.py` keeps a stored row only under the same code fingerprint, which hashes the run's `models/` and `data/`, and the run itself writes there after the batch: `models/decision_tests/`, the compute ledger, `data/input_checks.json`. That left 0 of 256 and 0 of 20 rows eligible. The new `toolkit/analysis/row_reuse.py` gives any batch with a fixed results path the reuse #241 gave the joint calibration. Rows come only from trusted files, those whose recorded digest equals the file's (`joint_calibration._trusted_sources`). A row answers a job when its `job_sha`, its engine identity and the adapter digest (`joint_calibration.adapter_digest`) are the current ones. Rows recorded with no adapter are admitted only when `$MA_JC_LEGACY_ADAPTER_SHA256` attests the current digest. No row file is lost: the directory's trusted files are archived under `<dir>/rows/<k>/` before anything rewrites them, and so are the files a batch of the remaining jobs writes. The results file at its fixed path is then republished in job order with a digest sidecar. `run.py` (the outcome batch) and `boundary.py` (the boundary batch) call `row_reuse.run`. The agent-written `models/ext/` stays in `compute.py`'s fingerprint. `toolkit/analysis/batch.py` and `toolkit/engines/horizon.py` are unchanged, so the adapter digest stays 48226c2b…. Self-tests RR1-9: RR2 reproduces the F6 run 2 failure, and RR9 failed first. Retro-proof on a copy of F6 run 2's run dir: outcome, 8,192 of 8,192 jobs rebuilt by `batch.design` are admitted; boundary, 69 of 69 stored rows are trusted with the current engine identity and an attested adapter; calibration, 3,090 rows eligible via #241.
