## Changelog

**World-model trials: version 0 of the world model written before any simulation, registered in remote git, confronted with a small engine sweep, on many low-compute questions.** A bounded seed task (`agents/v2_sdk_tasks.py` `seed_world_model`: one SDK session, file tools only, a USD cap, the decision design principles and the world model's own seed and test documentation, read from `toolkit/analysis/world_model.py`'s docstring) writes `world_model_seed.yaml`. It cannot read the run's `analysis/` or any other run. The harness checks the seed with `world_model.validate` (the validator `register` and `build` use) and against the design's package and feature names, from `world_model.design_features`, which `load_sweep` now uses too. It asks for one repair. `scripts/world_model_trials.py` runs each question through prepare, seed, register (the world model CLI), then the ledger and seed alone committed to branch `wm-trials` in its own worktree, pushed without force and fetched. Next comes a local batch of at most 50 engine runs on 2 worker processes, with `record_first_seen` called by the driver, and `world_model build --anchor-ref refs/remotes/origin/wm-trials`. LLM steps run in parallel (default 5) and engine steps in one queue. Spend goes to `trials/spend.jsonl`, an append-only, hash-chained ledger across invocations: a task's cap is reserved before launch and refused when committed spend plus the cap would pass `--total-cap-usd`. Completed questions are skipped on rerun. `score` writes `trials/summary.yaml` and `summary.md`: statuses, confirmation by confidence, contradictions and their open questions, where_to_look's top item, and a failure-mode taxonomy. `scripts/world_model_trials_questions.yaml` holds 10 questions (the five public eval-suite questions and five synthetic ones) on templates under `data/world_model_trials/` for the package-rate (trial_priors), compartmental and renewal engines.

Later rounds on the same PR (2026-11-13). A seed sees no spec values, effect priors, or input data, and from batch 4 on it sees the pre-registered willingness to pay: a published threshold and DALYs per outcome type. Citations are looked up in OpenAlex, then Semantic Scholar, then Crossref; a citation that is not found is only a flag. Claims fixed by declared inputs are set aside and never scored. Features declared independent must also be uncorrelated in the realized table. The engine step runs in a Coiled VM job, with the job's real cost recorded in the spend ledger. `toolkit/analysis/belief_table.py`, the simpler structure of docs/design/v2-progressive-steps.md §4–5, scores each claim against its probability p: surprise, calibration by p-bin, Brier and log score per batch, a stated update rule, and the next simulation where decides is yes and p is nearest 0.5. One guard (`guard_reasons`) replaces the separate classes.

Belief table v2 (owner, 2026-11-14). Each hypothesis is now a set of competing claims with weights that sum to 1: "increases", "decreases" and "no material effect" for a direction test, "holds" and "does not hold" for any other test. A belief that rests on our engine only also carries "simulator artefact" in its world layer. A seed may state the weights; otherwise the remainder 1 - p is split equally. An evidence log holds one row per item: source, type (trial, observational, our_sim, expert), the claim it favours, and a likelihood ratio derived from the test result alone. A decided test counts 10. An undecided one counts 1, 1.5 or 2 toward the sign of its estimate, set by how far its p value is from no effect. A marginal-only result counts at most 2. Each row also names a dependence group: one engine on one design is one group, counted once. Weights are updated in odds form, one ratio per group, and nothing is overwritten. Our simulations update an engine layer and papers and data a world layer. Where the two lead with different claims, a check item names the simulator, the test or the literature to check. A chained question carries every claim set with its weights and its full evidence log, including inconclusive results with their rho, interval and p. A scored claim's p is its weight before the question's own evidence, so Brier, log score and surprise are unchanged for unchained questions. Seeds must state adjust_for on a direction test of a feature that is not sampled independently. The VM's engine step takes `--workers`; more than 2 workers are allowed only inside a VM job.
