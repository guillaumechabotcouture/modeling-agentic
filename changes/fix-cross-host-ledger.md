## Changelog

**v2: a compute reservation left by a dead caller on another host is settled, and a moved run dir still finds its progress record.** The Nigeria v2 full run (2026-11-02): the analyze step's engine batch (dask backend) was killed by the step timeout and left one reservation of 432,000 core-s (120 core-hours of the 200 run cap) in `models/compute_ledger.json`. The run was resumed on a new cluster, with a different hostname and checkout path. `scripts/compute.py` `_live_reservations()` held every reservation from another host for as long as it existed, so this one would have stayed held for the rest of the run. Its `progress` path also pointed into the old checkout, so settling it would have found no record. Three changes. (1) Heartbeat: a ledgered call now rewrites its progress record's `t` every `PROGRESS_HEARTBEAT_S` (30 s) from its own thread, also while a single task runs for hours. Before this change the record was rewritten once per dispatch loop (dask) or per submission (local), so the local backend could leave it unchanged for as long as a task ran. The record carries `hb_s`. A reservation from another host whose record has not been refreshed for `PROGRESS_STALE_S` (300 s, ten heartbeats, which also covers clock skew between hosts) is settled (`_foreign_dead`). A record without a heartbeat (written before this change) is settled after 300 s only if it was kept in another run dir, because its caller can no longer release that copy; otherwise it is settled after `PROGRESS_STALE_LEGACY_S` (24 h, the longest step limit). With no readable record, the reservation is held for 24 h from its reservation time and then charged in full. No reservation is held forever. (2) The settle charge for a caller on another host: nothing is signalled from here. Its pids belong to that host, and its scheduler may be gone. Its remote chunks are therefore bounded by their shares plus the stop grace, as `_settle_dead` already bounded unconfirmed remote chunks. Local work in flight, which has no share, charges the reservation, and so does an unreadable record. (3) Paths: reservations record the progress path relative to the run dir. An absolute path from before this change that points into another run dir is found by its `.compute_progress/<name>` suffix in this one (`_progress_path`). Self-tests, written first: XH1-XH7 in `scripts/compute.py` (a stale cross-host record is settled from its record and signals nothing locally; a fresh one is held; a legacy record is held within 24 h and settled past it; a moved run dir resolves the old absolute path, also for a dead same-host caller; an unreadable or missing record is held, then charged in full; cross-host local work in flight charges the reservation; a running call writes a relative path and refreshes its heartbeat during a long task). Retro on a synthetic ledger with the same shape (8 chunks of 8 tasks in flight, 158,572.8 core-s done, 432,000 reserved, run dir moved): the reservation is still held when the run is resumed 2 min after the kill, and is settled when it is resumed 1 h after. The chunks' shares (the remaining allowance split over the slots) sum to 273,427 core-s, so the bound reaches the reservation and the charge is the full 120 core-hours. With 5,000 core-s shares, the charge would be 55.4 core-hours.
