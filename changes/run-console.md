## Changelog

**The run console: a local page for the owner of a v2 run.** Design: `docs/design/v2-run-console.md`. `scripts/run_console.py` (stdlib `http.server` on 127.0.0.1 only, a per-process token on every POST, a Host check) serves `scripts/run_console.html` (vanilla JS, a small local markdown renderer, no CDN). The main pane is one chronological stream rebuilt from the run's artifacts: stage changes with why and spend (`run_state.json` through `stage_machine.load_state`), engine-batch progress with an ETA (`models/compute_ledger.json` reservations joined with `.compute_progress/`), figures with their provenance and captions, critique blockers with agree / disagree / comment, gate decisions, decision tests, and "your decision needed" cards. A stepper over `stage_machine.STATES` shows done, current, waiting, failed and skipped states, the round and the fix-loop count, and filters the stream by stage. Answers change a run only through the existing commands: `agents/stage_machine.py sign --by owner`, `scripts/scope_signoff.py sign --answers` (read back by `load_answers`), or `cloud/run_cluster.py <config> sign` for a mirrored run; each needs an explicit confirm and the owner's note. Chat goes to `claude-opus-5-5` through the official SDK (`anthropic==2.3.0`, new pin, imported on the first message): streamed, adaptive thinking, effort set explicitly, server-side refusal fallback, the rules and the run context as two cached system blocks, `[[file#anchor]]` citations that open the side panel, uncited numbers marked, a per-message cost from `usage` and a session cap (default $2) checked before each call. Guidance and corrections go to `<run_dir>/owner/feedback.jsonl` (anchor, kind, layer, optional proposed change) before Claude acknowledges them; the turn is kept in `owner/chat.jsonl`. A learning view lists feedback across runs by layer and exports a digest. The sidebar lists runs under `--roots`; "Build on this run" writes a draft under `<root>/_drafts/` (spec, derivations, engine choice, and each stored batch's reuse verdict from `compute.code_fingerprint`) and shows the commands, launching nothing. The compute panel runs `run_cluster.py <config> status|health|report-cost` read-only, at most once a minute and only while "live" is on. Self-tests RC1-RC11 were written first (α) on a synthetic run dir. (γ) Without --port a busy default port falls through to the next free one (an explicit busy --port is a one-line error), and a placeholder ANTHROPIC_API_KEY counts as missing (RC12, RC13). (δ) A calmer page after the owner found it cluttered: one sans font (mono only for ids and paths in the side panel), a short one-line title with the full question in a collapsible "Question" section, sidebar runs labelled by folder (F1, F2_baseline) with a state chip, the headline number and the date, a thin dot stepper (FIX_LOOP, OWNER_DECISION and PRESENTATION collapse when never entered; the failed state is a small red dot with its reason on hover), a status line of at most four plain items, transitions as single lines, one card style, a sticky composer, and a phone layout. Live vs finished: an ETA only while the run is live; a progress record left on a finished (or stale) run reads "interrupted"; compute used = settled ledger core-seconds plus live progress (RC14). (ε) The sidebar is a project with a run lineage: runs of one question grouped, newest on top, each with a short label, a status chip, the headline number, and its relation to the previous run (resumed, amended + re-signed, relaunched) with the scenario as a structured diff of the signed spec's lineage fields; the selected run expands to engine and version, why it ended, outcome and package shift, spend, spec sha, sign-off and path. Staging copies (never past sign-off, or byte-identical copies) are listed as drafts. Shift-click compares two runs (spec diff, engines, outcome, package counts, decision tests). A Figures view shows the run's figures as a captioned grid, with a one-line reason when there are none (RC15). (ζ) Tables and reader support: a summary of key numbers with units and source files at the top of each run; the gate's done-when status as a table grouped by blocker; blockers per critique round and decision tests as tables; results.md tables with right-aligned, separated numbers and a muted title; each card says what it is and whether it needs the owner; a module glossary (definitions with their source files) behind hover on pipeline terms, and benchmark ids from the engine card; why an unfinished run stopped, from its journal and the latest operator note; compute used with reused engine-batch points and the run they came from; no JSON shown to the reader (RC16). (η) Failures are visible: a failed fetch or render shows a one-line banner with Retry; fetches time out (60 s) instead of hanging; the sidebar says "Loading runs…" until /api/runs answers; `[hidden]` always hides (the banner's flex display had overridden it); the page checks that /api/runs carries every key it reads (RC17). (θ) Faster loads: parsed artifacts are cached by file mtime and size (YAML through the C loader when available), and the server warms the cache at start. On the owner's real roots /api/runs went from about 500 ms to 8 ms warm (600 ms on the first request after start), and the first /api/run from about 700 ms to 10-20 ms (RC18). (ι) Plain words: a done-when pattern reads as its alternatives ("mentions one of: status quo, business as usual, …"), the pattern on hover; a decision test shows its parameter and the value's unit from the engine card, its question's first sentence (the rest on "more"), and a hint for "re-solved vs point plan"; a stopped run is one line ("Stopped during fix loop, round 1; no reason recorded") with the latest operator note behind "note", quoted only when dated after the run's last transition; the project is named by the question's first clause; the sidebar's two largest package shifts spell components out from the question (cm → case management) and are ranked by units moved times the share moved (RC19). (κ) `--mirror` combines with `--roots`: a mirrored live run joins the same project's lineage, marked "live mirror"; a run sitting directly under a named root (the mirror's `live/<run>`) is labelled by that root (RC20).
