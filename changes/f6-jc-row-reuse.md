## Changelog

**The joint calibration reuses stored unit runs by job_sha and engine identity.** F6 run 1 (2026-11-16) stopped in calibration after 3,088 unit runs, which cost about $114. `compute.py` reuses a stored row only under the same whole-repo code fingerprint, so any harness edit (for example a calibration acceptance rule) would recompute every one of them. `toolkit/analysis/joint_calibration.py` now reads every row already stored under `analysis/joint_calibration/call*/results.jsonl` before the run rewrites any file (`stored_rows`). `Simulator._units` sends to the engine only the jobs no stored row answers. A stored row answers a job when `batch.verify_rows` admits it: the row's `job_sha` equals the job's (every input: engine reference and config, horizon, windows, unit, package, params, seed), and its engine identity (code, parameters, configuration) equals the current engine's. This is the check `load_prior` already applies to earlier runs. The call's results file is republished in job order, from the stored rows plus the computed rows whose `job_sha` matches, never a stale row, and before any batch failure is raised, so the stored rows stay on disk. The report records `adapter.stored_rows_reused`. The CLI gains `--reuse-check`, a read-only count by call of the stored rows the current engine identity admits. Residual risk: harness code that wraps the engine call (`batch.run_job`, `make_horizon`) is not part of the engine identity, so a change there that alters results without changing a job's inputs would not be detected. Self-tests JA26a-h: JA26a, b and e failed first. Retro-check on F6 run 1's stored rows: `--reuse-check` finds 3,088 stored and 3,088 admitted (call1 1,236, call2 1,236, call3 309, call1001 307). Job-level check with this code: wave 1 1,234 of 1,236 admitted, plus 2 equal to one ulp of m0 (a laptop-against-VM rounding difference); verification 309 of 309.
