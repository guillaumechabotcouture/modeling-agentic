## Changelog

**A signed spec can set an engine parameter's point value: `engine_parameters` (owner decision 2026-11-02).** The Nigeria headline depends on the ITN effect. At the malaria engine's card value for net retention, the held-out nets-versus-none benchmark B7 is out of band; at a shorter value, B7 and B8 are both in band. The owner chose to run the headline at the shorter value and report the card value as a decision test. Until now the spec could not set a point value: `engine.config` holds constructor arguments, `uncertainty.priors` covers draws only, and a `parameter_value` test changes a value only inside the test. The new top-level section is `engine_parameters: {<name>: {value, units?, source, reason, outside_card_range?, range?, dist?}}`, defined in `toolkit/spec/engine_parameters.py` and checked by `schema.validate`. A spec value is a scenario choice the owner signs. It is not an engine change and not a fit. Checks: the parameter is on the engine card and of kind `fixed` or `scenario`; fitted and calibrated parameters are refused, and a unit attribute is refused with a pointer to where it is bound. `source` and `reason` are required, and `units`, when given, must equal the card's. A value or range outside the card's range needs `outside_card_range: true`; the card's range is the parameter's `lo`/`hi`, else its card prior's range, and the flag is refused where it does not apply. `uncertainty.priors` cannot also name the parameter, and `analysis_settings.yaml` cannot set it. With `engine: auto`, the shape is checked at sign-off and each candidate is checked against its own card. Application: one function, `params(spec, theta)`, puts the spec values under every parameter set where one is first built (`Analysis.theta0`, the emulator's batch jobs and the calibration's `Likelihood`); draws and decision tests that set the parameter still win. Without `range`, the value is held fixed (a card prior on it is not drawn), and the interval label says "held fixed at the spec value" (a new `spec_fixed` key in `render_claims.interval_label`). With `range` and `dist`, it is a prior with its mode at the spec value. On the emulator path, a held value that a `parameter_value` test varies is a design input over the box from the spec value to the tested values (`spec_value_names`, `spec_value_ranges`), so a test at the card value runs. The result file records `spec_value: {value, card_value, card_value_tested}`, and the statement says in words that the headline uses the spec value. Reporting: the engine artifact (`spec_values`), results.md (numbers from `spec_value.*` claims), the report's harness block and the sign-off sheet each name the value, its source and reason, and the card value and range it replaces; a value outside the card's range is a HIGH note. The parameters figure shows it as "spec value", with the card value marked. Specs without the field keep byte-identical job hashes, checked against golden digests from c0ed767. Tests, written first: `engine_parameters` EP1–EP25 (schema refusals; sign-off hashing; job hashes; what every engine call received on a recording toy engine on the emulator path, worker processes, schedule and trajectory tasks included, and on a direct path with likelihood calibration; the UI label; the decision test at the card value; results.md, the report block, the engine artifact and the figure), `signoff` SG11–12, `render_claims` T1e–f, `figures` TT2e. Review round 2 (Codex), each test first: an `interaction_rescale` test with spec values reads its arm ratios only from `benchmarks_at_spec_values.yaml` beside the spec (the benchmark runner at the spec values, provenance and `spec_parameters` checked; `engine_parameters.py benchmarks <pack> <spec>` writes it), else it is not run (EP26–28); interval labels accept the engine contract's parameter names such as `efficacy:vax` (T1g–h); a ranged spec value whose priors are excluded is held and so is an emulator input for a test that varies it (EP29); the sign-off sheet normalises string engine refs and `engine: auto` (pre-sign candidates, or a note that the card values are not yet known) (SG13–15); the parameters figure keeps the card range and the draw range apart (TT2f); a range that leaves the card's range is named as the range (EP7i–j). Review round 3 (Codex), each test first: the benchmark arms at the spec values are a harness output (`analysis/benchmarks_at_spec_values.yaml`, written only by the `benchmarks` harness step, also listed in v1 SCRIPT_OUTPUTS) with a harness record of the file's digest, the values and each arm's engine and configuration; verification reads the record and recomputes each arm's engine identity, and both files are inputs of the decision-test artifact, so an edit invalidates the run (EP30, EP32–35); the pack's engine must be the run's engine and the stamp names the engine the arms ran with (EP31); in those arms a benchmark setting's own parameters win over spec values, which replace only engine defaults (`Runner(base_params=...)`; EP36–37 on the real B15 Muleba setting, 949 days kept); the sign-off sheet keeps each pre-sign candidate's configuration (SG16). Review round 4: the harness record also carries the full configuration digest (run and each arm), verified beside the engine identity, which leaves out some dynamics settings (a CompartmentalEngine record made with generation_interval [1.0] is refused for [0.5, 0.5]; a record without the digest is refused; EP38–39); with `engine.candidates` in the spec, the sheet merges the refs with the pre-sign check's candidate configurations (SG17).
