## Changelog

**Direct evaluation: uncertainty draws fan out over the run's compute workers.** In the hb1 eval run flu_vaccine R2 (direct evaluation), the 200 uncertainty draws ran serially in the analysis process for 14.6 h while the compute workers were idle. When the run has compute workers (`MA_COMPUTE_SCHEDULER`) or the caller passes `draw_fanout: true` in compute_kw, `uncertainty._draw_rows` now samples a wave of draws in order (`draw_fanout.WAVE`, 50). It sends their engine runs through `scripts/compute.py` `map_fn` (`toolkit/analysis/draw_fanout.py::run_task`), then evaluates each draw in order on its prefetched runs (`DirectModel.use_runs`: taken once, and only at the same parameters, unit values and pairs; fails closed otherwise). Without workers the draws run in-process as before. A task is one draw's pairs, cut exactly as `DirectModel._runs` cuts them in-process: `run_batch` calls of `BATCH` members, or one `run()` per pair. Every engine call therefore has the same members, and the results do not depend on the number of workers. Each task result carries its input sha256 and the engine identity, both checked on return. The figure step's check of the stored draws (α) uses the same path. A run whose draws fanned out writes `analysis/draw_fanout.json` (backend, tasks, workers, wall time). Only engines that declare `batch_equals_run` (today the compartmental engine) and whose input files lie where compute.py ships them fan out; any other keeps its draws in-process and logs why. The Codex review found that the package-rate engine multiplies rate ratios in hash-seed order. Tasks return only the metadata the model reads, waves are bounded by engine runs (`WAVE_PAIRS`), compute calls stay within `max_tasks`, `analysis.workers` caps the workers, and a rerun clears an earlier `draw_fanout.json`. Self-tests DF1–DF15: DF2 checks that `uncertainty.yaml` is identical in-process and over 1 or 3 workers.
